# Проектные решения безопасности

Все решения относятся к модели и допущениям [THREAT_MODEL.md](THREAT_MODEL.md). Будущие проверки ниже описывают, как команда будет подтверждать механизмы; фактически выполненные проверки фиксируются отдельно в [VERIFICATION.md](VERIFICATION.md).

<a id="d-01"></a>
## D-01. Сервер хранит и проверяет сессии пользователей

**Контекст:** клиент управляет логином, паролем и заголовком `Authorization`. Серверу нужно определить, от имени какого пользователя выполняется защищённое действие, и сразу прекратить доступ после logout.

**Решение:**

1. При входе сервер проверяет пароль и создаёт случайный токен сессии.
2. В памяти сервера сохраняется не сам токен, а его SHA-256-хеш, идентификатор пользователя и срок действия — 30 минут.
3. Перед защищённым действием сервер находит сессию по токену, проверяет срок и загружает активного пользователя. Роль берётся из серверного состояния, а не из токена или JSON-запроса.
4. Logout удаляет текущую сессию. После перезапуска сервера сессии в памяти исчезают, поэтому требуется новый вход.
5. Пароли проверяются через `ASP.NET Core Identity PasswordHasher` с индивидуальной солью и 210 000 итераций. Вход ограничен десятью попытками с одного IP-адреса за минуту.

**Обоснование:** сервер может немедленно прекратить доступ после logout, удалив запись сессии. Пароль не хранится в открытом виде, а bearer-токен не становится источником роли или иных полномочий.

**Связанные угрозы:** [T-03](THREAT_MODEL.md#t-03), T-06, T-07.

**Связанные требования:** [SR-01](SECURITY_REQUIREMENTS.md#sr-01), [SR-09](SECURITY_REQUIREMENTS.md#sr-09).

**Будущая проверка:**

- запрос без токена, с произвольным токеном, после logout и после перезапуска получает `401`;
- действующая сессия разрешает только действия пользователя, которому она принадлежит;
- 11-я попытка входа в минутном окне получает `429`, а после окончания окна вход снова доступен;
- ответы API, JSON-файл и журнал не содержат пароля или bearer-токена;
- отдельно планируется проверить саму границу истечения сессии при управляемом времени.

**Ограничения:** украденный действующий токен даёт права его владельца до выхода или истечения срока. Пользователь может иметь несколько сессий; logout отзывает только текущую. Лимит по IP может затронуть пользователей за общим адресом и не останавливает распределённый подбор. HTTP допустим только в локальной loopback-границе проекта.

### Сравнение применимых вариантов для управления входом

Продукту нужно обеспечить следующий процесс: пользователь входит в учебный аккаунт, выполняет действия от своего имени, а после выхода прежний токен больше не даёт доступ. В локальном однопроцессном API допустимо, что после перезапуска сервера пользователь входит заново.

| Ситуация в продукте | Выбранный вариант: сервер хранит сессию | Альтернатива: подписанный JWT-токен |
| --- | --- | --- |
| Пользователь выполняет вход | Сервер создаёт случайный токен и сохраняет связь «токен → пользователь → срок действия» в памяти | Сервер выдаёт токен с подписанными сведениями о пользователе и сроке действия |
| Пользователь нажимает «выйти» | Сервер удаляет сессию; прежний токен сразу перестаёт работать | Подпись токена остаётся корректной до срока действия. Для немедленного logout всё равно нужен список отозванных токенов или актуальных сессий |
| Сервер перезапускается | Сессии в памяти исчезают; пользователь входит повторно | При сохранённом ключе подписи старый токен может продолжить работать после перезапуска |
| Позже появится несколько экземпляров API | Понадобится общее хранилище сессий, чтобы любой экземпляр видел logout | Подпись можно проверить на любом экземпляре, но для немедленного logout и актуальных ролей всё равно нужен согласованный механизм отзыва или проверки состояния |
| Цена решения сейчас | Для одного локального API достаточно памяти процесса; недостаток — повторный вход после рестарта | Нужно безопасно хранить ключ подписи, определить срок токена и отдельно решить, как немедленно отзывать токены |

**Выбор и компромисс:** выбраны серверные сессии с непрозрачным токеном. В текущем продукте важнее немедленно прекратить доступ после logout, чем сохранять вход после перезапуска. Для одного локального процесса удаление записи сессии проще, чем выпуск JWT вместе с отдельным механизмом отзыва.

**Когда пересмотреть решение:** если потребуется сохранять вход после перезапуска или запускать несколько экземпляров API. Тогда нужно сравнить общее хранилище серверных сессий и JWT с механизмом отзыва: сам переход на JWT задачу logout не решает.

**Проверка ограничения:** пользователь выполняет вход, выходит и повторяет запрос со старым токеном. Ожидаемый результат — `401`. После перезапуска старый токен также получает `401`, а новый вход создаёт рабочую сессию.

<a id="d-02"></a>
## D-02. Сервер сам определяет, кто и что может сделать с обращением

**Контекст:** HTTP-клиент может передать любой ID обращения, статус или дополнительные поля JSON. Нельзя считать, что клиент действительно является автором обращения или имеет полномочия operator.

**Решение:** перед выполнением операции сервер:

1. определяет текущего пользователя по действующей серверной сессии;
2. находит обращение по ID;
3. проверяет, разрешено ли этому пользователю требуемое действие;
4. только после этого читает или изменяет обращение.

Автор обращения может работать только со своим обращением. Operator может читать все обращения, добавлять комментарии и менять статус в пределах своей роли. Комментарии наследуют доступ от обращения: нельзя прочитать или добавить комментарий к чужому обращению.

При создании обращения сервер сам назначает автора из сессии. Поля `ownerId` и `role` от клиента не принимаются. Изменение статуса и чтение журнала доступны только operator; operator не может менять текст обращения от имени автора.

**Обоснование:** ID обращения не является секретом: пользователь может узнать или подобрать его. Поэтому скрытая кнопка, отсутствие ссылки в интерфейсе или знание ID не должны определять доступ. Сервер проверяет право на конкретное обращение при каждом защищённом действии, включая связанные комментарии.

**Связанные угрозы:** [T-01](THREAT_MODEL.md#t-01), [T-02](THREAT_MODEL.md#t-02), T-06.

**Связанные требования:** [SR-02](SECURITY_REQUIREMENTS.md#sr-02), [SR-03](SECURITY_REQUIREMENTS.md#sr-03), [SR-04](SECURITY_REQUIREMENTS.md#sr-04).

**Будущая проверка:**

- Alice создаёт обращение и комментарий.
- Bob знает ID этого обращения и пытается прочитать, изменить его, прочитать комментарии и добавить новый комментарий.
- Сервер не раскрывает данные и не изменяет обращение.
- Alice может работать со своим обращением; operator может прочитать его и выполнить разрешённую операцию.
- User получает отказ при смене статуса и чтении журнала.
- Operator получает отказ при попытке изменить текст обращения автора.
- Попытка передать `ownerId` или `role` в JSON отклоняется и не создаёт обращение от имени другого пользователя.

**Ограничения:** operator сознательно имеет доступ ко всем обращениям. В продукте нет подразделений, отдельных очередей или назначения обращения конкретному оператору. Защита относится к HTTP API и не защищает файл хранилища от владельца операционной системы.

<a id="d-03"></a>
## D-03. Сервер принимает изменение обращения как одну согласованную операцию

**Контекст:** автор и operator могут работать с одним обращением одновременно. Если каждый запрос отдельно проверит состояние `New`, но изменит обращение позднее, автор может переписать текст после того, как оператор начал обработку. Также нельзя считать операцию успешной, если обращение или событие аудита не удалось сохранить в файл.

**Решение:** два клиента могут отправить изменение одновременно, но сервер выполняет критическую часть только по одному запросу. Каждое изменение содержит `expectedVersion`.

Перед изменением сервер получает блокировку `SemaphoreSlim`. Пока первый запрос проверяет обращение, применяет изменение, сохраняет файл и повышает версию, второй запрос ждёт освобождения блокировки. После этого второй запрос проверяет уже актуальную версию. Если он был подготовлен для старой версии, его `expectedVersion` не совпадает с текущей версией обращения: сервер возвращает `409` и ничего не изменяет.

Само изменение выполняется в одной критической секции:

1. создаётся рабочая копия состояния;
2. проверяются текущий пользователь, доступ к обращению, его состояние и актуальная версия;
3. применяется изменение, увеличивается версия и добавляется событие аудита;
4. вся рабочая копия записывается во временный JSON-файл и заменяет основной файл;
5. только после успешной замены файла новое состояние публикуется в памяти.

Автор изменяет текст только в `New`. Operator меняет статус только по переходам `New → InProgress → Resolved`. После `Resolved` новые комментарии не добавляются. Если версия устарела, состояние недопустимо или запись файла завершилась ошибкой, изменение не принимается.

Технически критическая секция реализована через `SemaphoreSlim`, а `Store.WriteAsync` публикует рабочую копию в памяти только после успешного `File.Move` временного файла.

**Обоснование:** проверки до записи недостаточно: между проверкой и изменением другой пользователь может изменить состояние обращения. Версия и общая критическая секция связывают проверку с самим изменением. Запись обращения и аудита в одном снимке не позволяет принять обращение, но потерять запись о принятом действии.

**Связанные угрозы:** [T-04](THREAT_MODEL.md#t-04), [T-08](THREAT_MODEL.md#t-08), T-06.

**Связанные требования:** [SR-05](SECURITY_REQUIREMENTS.md#sr-05), [SR-06](SECURITY_REQUIREMENTS.md#sr-06), [SR-08](SECURITY_REQUIREMENTS.md#sr-08), [SR-10](SECURITY_REQUIREMENTS.md#sr-10).

**Будущая проверка:**

- автор и operator получают обращение в состоянии `New` с версией `v`;
- автор редактирует текст, а operator принимает обращение, передавая одинаковый `expectedVersion = v`;
- принимается ровно один запрос, второй получает `409`;
- версия становится `v + 1`, итоговый текст и статус соответствуют принятому запросу, а в аудите появляется одно событие;
- после перехода в `InProgress` автор не может переписать текст даже с актуальной версией;
- при искусственной ошибке замены файла API возвращает `500`, а память, файл и аудит сохраняют прежнее состояние;
- после успешной записи и обычного рестарта сохранённые обращение, комментарии, версия и аудит доступны.

**Ограничения:** блокировка действует только внутри одного процесса. Полная копия и запись JSON-файла подходят для малого учебного продукта, но не для высокой нагрузки. Замена файла не гарантирует сохранность при отключении питания. После `409` клиенту нужно перечитать обращение; ключей идемпотентности для восстановления после потери HTTP-ответа нет.

### Контрпример и уточнение цепочки

**Исходное предположение:** достаточно отдельно проверить, что автор является владельцем обращения, а его статус — `New`.

**Пограничный случай:**

1. Автор и operator читают обращение в состоянии `New`, версия `v = 1`.
2. Автор начинает редактирование и проходит проверку `New`, но ещё не сохраняет текст.
3. Operator переводит обращение в `InProgress`.
4. Автор сохраняет другой текст. Без совместной проверки он может изменить уже принятое в работу обращение или вернуть старое состояние `New`.

**Последствие:** два разрешённых по отдельности действия нарушают целостность обращения и меняют предмет работы operator.

**Уточнённая цепочка:** T-04 → SR-05, SR-06 → D-03 → конкурентная проверка. Один запрос принимает изменение, второй получает `409`; итоговое обращение соответствует единственной принятой операции.

## D-04. Сервер принимает только ожидаемый JSON-ввод ограниченного размера

**Контекст:** клиент полностью управляет JSON-запросом. Он может передать дополнительные поля, пустой или слишком длинный текст, некорректный JSON либо чрезмерно большое тело запроса.

**Решение:** сервер принимает DTO с заранее определёнными полями. Дополнительные поля JSON отклоняются, а до изменения состояния проверяются:

- наличие и непустое значение текста;
- максимальная длина логина, пароля, темы, описания и комментария;
- отсутствие NUL-символа;
- общий размер тела запроса — не более 16 КиБ.

Технически неизвестные поля отклоняет `UnmappedMemberHandling.Disallow`, размер тела ограничивает Kestrel, а содержимое строк проверяет `Rules.Text`.

**Обоснование:** ограниченный JSON-контракт не позволяет незаметно передать владельца или роль обращения. Проверка до изменения не допускает непригодные данные в хранилище, а предел тела ограничивает потребление памяти одним запросом.

**Связанные угрозы:** T-02, T-05, T-07.

**Связанные требования:** [SR-03](SECURITY_REQUIREMENTS.md#sr-03), [SR-07](SECURITY_REQUIREMENTS.md#sr-07).

**Будущая проверка:**

- запросы с пустым текстом, NUL-символом, некорректным JSON или неизвестным полем получают `400`;
- запрос с телом 20 000 байт получает `413`;
- после каждого отказа обращение, комментарии, версия и аудит не меняются;
- при появлении frontend отдельно проверить безопасное отображение текста: защита от XSS в текущем API без HTML-интерфейса не заявляется.

**Ограничения:** предел одного запроса не ограничивает общее число обращений, суммарный размер файла или количество одновременных клиентов. Лимит символов и лимит байтов UTF-8 различаются, поэтому применяются оба. При расширении продукта потребуются пагинация и квоты.
