# Требования безопасности

Объекты и последствия нарушения описаны в [PROJECT.md](../PROJECT.md#5-значимые-данные-и-другие-объекты). Требования относятся к однопроцессному локальному HTTP API.

## SR-01. Действующая серверная сессия

**Требование.** Сервер выполняет защищённые операции только от имени пользователя с действующей серверной сессией. После выхода, истечения сессии или перезапуска сервера прежний bearer-токен не даёт доступа.

**Критерий приёмки.**

- **Ситуация:** клиент отправляет защищённый запрос без токена, с вымышленным токеном, после logout или после перезапуска сервера.
- **Ожидаемый результат:** сервер возвращает `401`; данные и журнал изменений не меняются.
- **Ситуация:** клиент использует действующий токен.
- **Ожидаемый результат:** сервер определяет пользователя по серверной сессии, а не по данным HTTP-запроса.

**Связанные T / D:** T-03 / D-01.

## SR-02. Доступ к обращению и комментариям

**Требование.** Сервер разрешает пользователю читать и изменять только собственные обращения о технических проблемах на семинаре. Читать и добавлять комментарии пользователь может только к доступному ему обращению. Оператор может читать все обращения и их комментарии.

**Критерий приёмки.**

- **Ситуация:** Alice создала обращение и комментарий; Bob знает идентификатор обращения.
- **Действие:** Bob запрашивает список, само обращение, его изменение, список комментариев и добавление комментария.
- **Ожидаемый результат:** обращение отсутствует в списке Bob; запросы к обращению и комментариям не раскрывают данные и не изменяют их; версия и журнал не меняются.
- **Позитивный случай:** Alice и operator могут прочитать обращение; Alice может выполнить разрешённое изменение.

**Связанные T / D:** T-01 / D-02.

## SR-03. Серверное назначение автора обращения

**Требование.** При создании обращения сервер назначает автора по действующей серверной сессии. HTTP-клиент не может выбрать владельца обращения или роль автора через JSON-запрос.

**Критерий приёмки.**

- **Ситуация:** Bob создаёт обращение, передавая идентификатор Alice либо дополнительное поле `ownerId` или `role`.
- **Ожидаемый результат:** запрос с дополнительными полями отклоняется; при корректном создании автором обращения становится Bob, определённый по его серверной сессии.
- **Неизменяемое состояние:** запрос не создаёт обращение от имени Alice.

**Связанные T / D:** T-02 / D-02.

## SR-04. Разделение полномочий user и operator

**Требование.** Сервер разрешает менять статус обращения и читать журнал успешных изменений только operator. Operator не может изменять заголовок или описание обращения от имени его автора.

**Критерий приёмки.**

- **Ситуация:** user с действующей сессией пытается изменить статус своего обращения или прочитать журнал.
- **Ожидаемый результат:** сервер возвращает `403`; состояние обращения и журнал не меняются.
- **Ситуация:** operator пытается изменить текст обращения.
- **Ожидаемый результат:** сервер возвращает `403`; текст и версия обращения не меняются.

**Связанные T / D:** T-02 / D-02.

## SR-05. Целостность жизненного цикла обращения

**Требование.** Автор может изменять текст только собственного обращения в состоянии `New`. Operator изменяет статус только по переходам `New → InProgress → Resolved`. После `Resolved` новые комментарии к обращению не добавляются.

**Критерий приёмки.**

- **Ситуация:** operator перевёл обращение из `New` в `InProgress`.
- **Действие:** автор пытается изменить его заголовок или описание.
- **Ожидаемый результат:** сервер возвращает `409`; текст, статус и версия не меняются.
- **Ситуация:** клиент запрашивает недопустимый переход статуса либо добавляет комментарий к `Resolved` обращению.
- **Ожидаемый результат:** сервер возвращает `409`; обращение и журнал не меняются.

**Связанные T / D:** T-04 / D-03.

## SR-06. Защита от устаревшего изменения

**Требование.** Сервер применяет изменение обращения только при совпадении `expectedVersion` с актуальной версией. Запрос с устаревшей версией не перезаписывает данные и не создаёт событие аудита.

**Критерий приёмки.**

- **Ситуация:** автор и operator получили обращение версии `v`.
- **Действие:** оба отправляют допустимое изменение с `expectedVersion = v`.
- **Ожидаемый результат:** принимается ровно одно изменение, версия становится `v + 1`; второй запрос получает `409` и не меняет обращение или журнал.

**Связанные T / D:** T-04 / D-03.

## SR-07. Допустимость входных данных

**Требование.** Сервер принимает от HTTP-клиента только допустимые поля и значения для входа, обращений и комментариев. Некорректный либо превышающий установленные пределы запрос не сохраняется и не изменяет состояние сервиса.

**Критерий приёмки.**

- **Ситуация:** клиент отправляет некорректный JSON, неизвестное поле, пустой текст, текст с NUL-символом либо значение длиннее допустимого предела.
- **Ожидаемый результат:** сервер возвращает `400`; обращение, комментарий, версия и журнал не меняются.
- **Ситуация:** размер тела HTTP-запроса превышает 16 КиБ.
- **Ожидаемый результат:** сервер возвращает `413`; данные не сохраняются.

**Связанные T / D:** T-05, T-07 / D-04.

## SR-08. Наблюдаемость успешных изменений

**Требование.** После каждого успешного создания, редактирования, изменения статуса или добавления комментария сервер сохраняет одно событие аудита. Журнал доступен только operator и содержит только метаданные, нужные для восстановления порядка изменений.

**Критерий приёмки.**

- **Ситуация:** Alice успешно создаёт или изменяет обращение; operator успешно меняет его статус.
- **Ожидаемый результат:** для каждого принятого изменения появляется одно событие с `actorId`, `ticketId`, действием, версией обращения и временем.
- **Ситуация:** запрос отклонён.
- **Ожидаемый результат:** событие успешного изменения не создаётся.
- **Ситуация:** user запрашивает журнал.
- **Ожидаемый результат:** сервер возвращает `403`.

**Связанные T / D:** T-06, T-08 / D-02, D-03.

## SR-09. Нераскрытие аутентификационных секретов

**Требование.** API не возвращает парольные хеши ни одному клиенту. Operator не получает пароли, парольные хеши или bearer-токены через журнал. Сервер не хранит исходные пароли и bearer-токены в постоянном файловом хранилище.

**Критерий приёмки.**

- **Ситуация:** клиент выполняет `POST /auth/login` и `GET /me`; operator выполняет `GET /audit`.
- **Ожидаемый результат:** успешный вход возвращает только новый токен текущего пользователя; ответы и журнал не содержат парольных хешей, паролей или bearer-токенов.
- **Ситуация:** проверяется постоянное файловое хранилище.
- **Ожидаемый результат:** в нём есть только хеши паролей, но нет исходных паролей или bearer-токенов.
- **Ситуация:** клиент передаёт неверный пароль либо неизвестный логин.
- **Ожидаемый результат:** сервер возвращает одинаковую ошибку без технических деталей.

**Связанные T / D:** T-03, T-06 / D-01, D-03.

## SR-10. Согласованное сохранение изменения и аудита

**Требование.** Сервер фиксирует изменение обращения и соответствующее событие аудита как одну операцию. Ошибка постоянного хранения не выдаётся клиенту за успешное изменение.

**Критерий приёмки.**

- **Ситуация:** сервер успешно сохраняет создание или изменение обращения, затем перезапускается обычным образом.
- **Ожидаемый результат:** после перезапуска доступны обращение, комментарии, актуальная версия и соответствующие события аудита.
- **Ситуация:** при сохранении искусственно возникает ошибка замены файла.
- **Ожидаемый результат:** сервер возвращает `500` без внутренних деталей; память, файл и журнал не содержат незафиксированного изменения.

**Связанные T / D:** T-08 / D-03.

## Связь с ограничением попыток входа

Ограничение попыток входа не стоит выдавать за полную защиту от отказа в обслуживании. Его можно оставить как уточнение D-01 и связанную проверку для T-07: один IP-адрес получает `429` на 11-й попытке входа в минутном окне. Если команда считает этот риск самостоятельным и значимым, его можно вынести в отдельное SR; для текущего локального стенда это необязательно.
