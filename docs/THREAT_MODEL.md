# Модель угроз

## Модель продукта

```mermaid
flowchart LR
    anonymous[Неавторизованный клиент]
    user[Пользователь user]
    operator[Оператор]

    auth([P1. Аутентификация и управление сессиями])
    tickets([P2. Операции с обращениями и комментариями])
    audit([P3. Чтение журнала аудита])

    sessions[(D1. Сессии в памяти: хеш токена, userId, срок)]
    store[(D2. store.json: пользователи, обращения, комментарии, аудит)]

    anonymous <-->|login/password; token или ошибка; TB-01| auth

    user -->|bearer token, ID обращения, текст, expectedVersion; TB-01| tickets
    operator -->|bearer token, ID обращения, текст, статус, expectedVersion; TB-01| tickets
    operator -->|bearer token; TB-01| audit

    auth <--> |проверка учётной записи и хеша пароля| store
    auth -->|создание, проверка и отзыв сессии| sessions

    tickets -->|проверка сессии и роли| sessions
    tickets <--> |чтение и изменение обращений, комментариев и аудита; TB-02 при записи| store

    audit -->|проверка сессии и роли| sessions
    audit -->|чтение метаданных аудита| store
```

**Что существует:** все показанные компоненты и Postman-коллекция из 12 ручных запросов. Автоматического набора интеграционных проверок сценариев обращений нет. Реального frontend и сетевого выпуска нет.

**Что планируется позднее:** проверки истечения сессии управляемым временем, долговременной нагрузки, устойчивости к сбоям ОС; расширение продукта по заданиям курса.

**Допущения:** один процесс API владеет файлом; сервер работает на loopback; все аккаунты и обращения учебные; ОС и оператор стенда доверены; operator вправе читать все обращения; внешние пользователи не имеют доступа к каталогу хранения. Публичные демонстрационные пароли не применяются для реальных данных или сетевого выпуска.

## Границы доверия

| Граница | Стороны и передаваемые данные | Причина проверки |
| --- | --- | --- |
| TB-01 | Клиент → API: login/password, bearer token, ID, текст, статус, expectedVersion | Клиент контролирует запрос целиком; ID и поля не подтверждают идентичность или права |
| TB-02 | Логика API → файловое хранилище: пользователи, заявки, комментарии, аудит | Успешная проверка и подготовка изменения в API ещё не подтверждают его устойчивое сохранение в файловом хранилище |

Внутри API граница между данными клиента и доверенной идентичностью проходит через проверку Sessions и загрузку активного User из Store. Роль из запроса не принимается. Объекты и последствия — [PROJECT.md](../PROJECT.md#5-значимые-данные-и-другие-объекты).

## Приоритетный набор

Выбраны T-01, T-02, T-03, T-04, T-08: изоляция пользователей, привилегии, идентичность и целостность записи необходимы для обоих основных сценариев. Угроза T-08 может возникнуть случайно — модель включает условия сбоя, а не только атаки.

Цепочки всего набора находятся в [D-01](DESIGN_DECISIONS.md#d-01), [D-02](DESIGN_DECISIONS.md#d-02) и [D-03](DESIGN_DECISIONS.md#d-03). T-05/T-06 также частично покрыты реализованными решениями; средний приоритет не означает отсутствия защиты. Для T-07 признан непокрытый риск общего роста данных.

До сетевого выпуска приоритет T-07 и риск передачи токена по HTTP должны быть пересмотрены. Атака администратора ОС на сам файл находится вне выбранной модели, и аудит не заявлен как защищённый от владельца компьютера.
