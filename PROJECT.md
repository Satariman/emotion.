# Паспорт проекта

## Общие сведения

**Название команды:** SeminarDesk (рабочее название).

**Название продукта:** СеминарDesk — сервис учебных обращений.

**Коды участников:** M1, M2.

**Статус ранней калибровки:** `черновик`; согласование преподавателя пока не получено.

**Исходное состояние:** исходный проект создан с нуля с помощью ИИ.
Ранее существовавшего кода и материалов нет. Допуск команды из двух необходимо
подтвердить у преподавателя. Соответствие кодов студентам передаётся закрыто.

## 1. Назначение

Сервис позволяет студенту оформить обращение о технической проблеме на семинаре,
следить за обработкой и обмениваться уточнениями с оператором. Оператор принимает
обращение и фиксирует завершение. Собственная предметная логика — права на заявку,
разрешённые переходы состояния и ограничение изменения описания после начала работы.

## 2. Граница продукта

**В продукт входит:** серверный HTTP API, вход в учебные аккаунты, заявки,
комментарии, переходы состояния, версии записей и журнал успешных изменений.

**Внешнее окружение:** терминал / HTTP-клиент, локальная ОС и файловая система. Внешних сетевых интеграций нет.

**Команда сознательно не реализует:** frontend, файлы-вложения, email-уведомления,
регистрацию, восстановление пароля, оплату, многопользовательскую администрацию,
распределённое хранение и промышленный выпуск.

## 3. Пользователи и доступные действия

| Роль | Кто это | Доступно | Недоступно |
| --- | --- | --- | --- |
| Без сессии | Неавторизованный клиент | /health и попытка входа | Заявки, комментарии и аудит |
| user | Автор обращения | Создать, читать свои заявки; редактировать свои New; комментировать свои незакрытые | Чужие заявки и комментарии; изменение статуса, владельца и роли; аудит |
| operator | Учебный оператор | Читать все заявки; комментировать незакрытые; переводить New → InProgress → Resolved; читать аудит | Создать заявку за пользователя; переписать его текст; поменять владельца; открыть Resolved заново |

## 4. Сквозные сценарии

### Сценарий 1. Создание и уточнение обращения

- **Участники:** user.
- **Начальное условие:** локальный сервер запущен, пользователь имеет учебный аккаунт.
- **Основные действия:** вход, создание заявки, чтение результата, исправление текста
  пока состояние New, добавление уточнения, повторное чтение состояния.
- **Результат:** собственная заявка зарегистрирована; пользователь видит только свои обращения.
- **Изменение данных:** новая заявка, её версия, комментарий и события аудита.

### Сценарий 2. Обработка оператором

- **Участники:** operator и автор заявки.
- **Начальное условие:** заявка в состоянии New.
- **Основные действия:** оператор читает список, принимает заявку с актуальной версией,
  отвечает комментарием и закрывает; автор видит ответ и состояние Resolved.
- **Результат:** обращение обработано, порядок действий наблюдаем в журнале.
- **Изменение данных:** состояние, комментарии, версии и события аудита.

## 5. Значимые данные и другие объекты

| Объект | Для кого значим | Последствия раскрытия | Последствия изменения / удаления / недоступности |
| --- | --- | --- | --- |
| Учётные записи и хеши паролей | Пользователи и оператор | Возможность офлайн-подбора после утечки хеша | Неверная роль открывает чужие заявки; потеря аккаунта блокирует доступ |
| Сессионный токен | Владелец сессии | Другой клиент сможет действовать от его имени до отзыва/истечения | Отзыв или потеря требует повторного входа |
| Заявки и комментарии | Автор и оператор | Чужой клиент узнаёт содержание обращения | Искажение проблемы, потеря уточнений или неправильная обработка |
| Статус и версия | Автор и оператор | Сам по себе статус малочувствителен | Гонка изменений приводит к потере правок и неверному этапу обработки |
| Журнал успешных изменений | Оператор и команда | Метаданные позволяют проследить обращения | Потеря события лишает возможности восстановить порядок изменения |

Используются исключительно вымышленные учебные данные; реальные сведения студентов
и соответствие M1/M2 аккаунтам не помещаются в публичные документы.

## 6. Компоненты и внешние взаимодействия

1. Терминал отправляет JSON-запросы серверу по HTTP на 127.0.0.1.
2. ASP.NET Core API разбирает DTO, проверяет сессию и полномочия, выполняет предметные правила.
3. Sessions хранит хеши непрозрачных токенов в памяти процесса.
4. Store хранит пользователей, заявки, комментарии и аудит в одном JSON-файле.
5. Доступ к Store сериализуется одной блокировкой; изменение записывается во временный
   файл и заменяет основной, затем публикуется в памяти.

Актуальная [модель архитектуры и границ доверия](docs/THREAT_MODEL.md#модель-продукта)
используется остальными документами по ссылке.

## 7. Откуда продукт получает данные

| Источник | Данные | Кто управляет | Использование |
| --- | --- | --- | --- |
| POST /auth/login | Логин и пароль | Клиент | Проверка учётной записи |
| Authorization | Bearer-токен | Клиент | Поиск серверной сессии; не источник роли |
| Путь запроса | ID заявки | Клиент | Выбор объекта с обязательной проверкой доступа |
| JSON тела | Текст, желаемый статус, expectedVersion | Клиент | Валидация и предметная операция |
| Конфигурация | Адрес сервера и путь хранения | Владелец стенда | Запуск и выбор файла |
| Файл хранилища | Аккаунты и состояние | Сервер; ОС находится вне модели атак клиента | Загрузка состояния при старте |

## 8. Минимальное функциональное ядро

**Обязательные функции:** вход/выход; создание и просмотр своих заявок; работа
оператора; чтение/добавление комментариев; версии и допустимые переходы;
локальное сохранение; проверяемое разграничение доступа.

**Можно исключить при нехватке времени:** расширенную фильтрацию, UI, вложения,
уведомления, статистику, поиск. Они не входят в текущую реализацию.

## 9. Стек и путь к первой работающей версии

**Основные технологии:** C# 12, .NET 8, ASP.NET Core Minimal API, System.Text.Json,
ASP.NET Core Identity PasswordHasher и стандартный rate limiter.

**Технологии, новые для команды:** участникам нужно подтвердить после разбора; их опыт не предположен.

**Внешние сервисы для запуска:** отсутствуют. После установки SDK API работает локально;
отказ внешних сервисов не меняет основные сценарии.

**Первый технический результат:** /health и серверная основа; в текущем комплекте
уже реализованы оба основных сценария. Реализация всех будущих этапов курса не заявлена.

## 10. Локальный запуск

**Требования:** .NET SDK 8.0.401 или более новый SDK ветки 8.0, терминал и curl.
Внешние сервисы и дополнительные NuGet-пакеты не нужны.

Из корня репозитория:

```sh
dotnet run --project src/Helpdesk.Api --launch-profile local
```

Сервер слушает `http://127.0.0.1:5080`. В другом терминале:

```sh
curl http://127.0.0.1:5080/health
```

**Ожидаемый результат:** HTTP 200 и `{"status":"ok","service":"rbpo-helpdesk"}`.
Это подтверждение запуска, а не доказательство всех свойств безопасности.
Остановка сервера — Ctrl+C.

При первом запуске в Development создаются открытые учебные аккаунты:

| Логин | Демонстрационный пароль | Роль |
| --- | --- | --- |
| alice | Alice-demo-2026! | user |
| bob | Bob-demo-2026! | user |
| operator | Operator-demo-2026! | operator |

Пример входа:

```sh
curl -X POST http://127.0.0.1:5080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"alice","password":"Alice-demo-2026!"}'
```

Полученный token передаётся как `Authorization: Bearer <token>` в защищённых
запросах. Срок сессии — 30 минут; выход и перезапуск прекращают её действие.
Попытки входа ограничены десятью на IP за минуту.

Состояние сохраняется в `src/Helpdesk.Api/data/store.json`, исключённом из Git.
Путь можно изменить переменной `HELPDESK_DATA_PATH`. Пароли хранятся как хеши,
сессии — в памяти процесса. Учебные пароли и локальный HTTP не предназначены
для сетевой эксплуатации или реальных персональных данных.
